# Design panel synthesis (raw, 2026-10-03)

This is the raw output of a five-lens design panel plus an adversarial completeness check. Where the COMPLETENESS CHECK section contradicts the synthesis, the check wins. Where docs/DECISIONS.md contradicts either, DECISIONS.md wins.


## feasibility

YES, the project is possible, and it is a good fit for one student in an intro Data Science course, but seven things in the description must change or be pinned down before any code is written:

1. ORDER OF WORK IS REVERSED. "Create a tabular dataset ... then simulate it" cannot happen in that order: the tabular dataset IS the log of the simulation. You build a small simulator first (weeks 1-2), run it many times with different seeds and settings, and the tables fall out of it. The dataset is still the graded deliverable; the simulator is the data generator.

2. "EACH ROAD HAS 4 WAYS, 2 SAME FLOW, 2 COUNTER FLOW" -> build ONE lane per direction in v1. If you meant 2 lanes per direction (dual carriageway), know that it drags in lane-changing, lane assignment by turn, and in-box parallel conflicts, which is more code than the rest of the simulator and changes nothing about what the traffic-light model learns. If you meant "each road is two-way and each junction has 4 arms", then 1 lane per direction is exactly what you asked for. Keep lanes_per_dir as a config value (default 1) so the choice is cheap to revisit.

3. "RED AND GREEN ONLY" IS FINE FOR THE DISPLAY, NOT FOR THE LOGIC. Amber exists to resolve the dilemma zone (a car too close to stop, too far to clear). Deleting it does not delete the physics. The signal plant must have an internal ALL-RED clearance state (minimum 4 s, extended until the box is clear of conflicting vehicles), a minimum green (5 s), a maximum green (60 s), and a per-car stop-or-commit rule evaluated once at the instant its light turns red. The lights still only ever show red or green; the dataset still only has two colours. The ML controller only REQUESTS a phase; the plant applies it when safe (a safety shield, exactly like a real signal cabinet).

4. TURNS NEED A PHASING DECISION. With one lane per approach, a car waiting to make the far-side turn blocks everyone behind it, and banning far-side turns makes 24 of the 56 origin-destination pairs unreachable on a "#" network. Resolution: SPLIT PHASING, one approach green at a time with all three of its movements (through, near-side turn, far-side turn) released together. Zero crossing conflicts, zero yielding logic, all destinations reachable, action space of exactly 4 per intersection. Capacity is lower, which is fine: demand is calibrated to it.

5. DESTINATIONS: use an 8x8 origin-destination matrix over the 8 road ends, sample a destination per car, compute its route once with Dijkstra on the 12-node graph, store the route. This gives every car a well-defined free-flow time and therefore a well-defined delay, which is the quantity every controller is judged on. "Random or fixed" is just which OD matrix you use.

6. "DIGITAL TWIN" NEEDS A PHYSICAL COUNTERPART. v1 is a simulation-based synthetic data generator (say so in the report). It becomes a twin in the extension only when there is (a) a "physical" system with hidden truth (a second run of the same simulator with hidden parameters and noisy detectors), (b) a twin model that sees only detector data and keeps a state estimate in sync, (c) a controller that reads the twin's estimate, never the truth, and (d) a monitor measuring twin-vs-physical drift. The dataset is designed from day one so that this is a column swap (obs_* columns, a source column, one shared build_features() function), not a rewrite.

7. "THE ML MODEL FOR ALL THE TRAFFIC LIGHTS" = ONE shared model applied at each of the four intersections (same features, same weights, neighbour information in the feature vector), trained on a table with one row per (intersection, decision instant). It is a ladder, not a single model: non-ML baselines (fixed-time, max-pressure) that must be beaten -> a supervised gradient-boosted classifier and regressor on your own table (the course deliverable) -> optional reinforcement learning (stretch). Honest expectation: a learned controller that ties max-pressure on the demand it was trained on and loses on unseen demand, reported cleanly with paired seeds and confidence intervals, is a strong course result.

Everything else in the student's description (per-car max speed, acceleration and braking drawn from distributions, more per-car indicators, four coupled intersections, later twin) is standard and buildable in plain Python (numpy, pandas, scikit-learn, matplotlib) in roughly 4-6 weeks part-time, provided cars are tracked in 1-D along lane edges (SUMO-style), not with free 2-D physics.


## arena

UNITS: SI throughout (m, s, m/s, m/s^2). Origin at the centre of the south-west intersection, x east, y north; the viewer flips y for the screen.

GEOMETRY ("#" network, all values config parameters):
- Two horizontal roads at y = 0 and y = 200, two vertical roads at x = 0 and x = 200. L_block = 200 m centre-to-centre (sweep 150 / 200 / 300 later). Road stubs extend L_stub = 150 m past the outer intersections to 8 boundary nodes. Arena bounding box x, y in [-150, 350].
- lanes_per_dir = 1, w_lane = 3.5 m, so every road is 7 m wide and every intersection box is a 7 m x 7 m square (w_box = 7).
- v_limit = 13.9 m/s (50 km/h) on every edge; set 11.1 m/s for 40 km/h Indonesian streets. Config value.

NODES (12): intersections I00=(0,0), I10=(200,0), I01=(0,200), I11=(200,200), ids 0..3 in that order. Boundary nodes W0=(-150,0), W1=(-150,200), E0=(350,0), E1=(350,200), S0=(0,-150), S1=(200,-150), N0=(0,350), N1=(200,350). Naming: W0 = west end of the y=0 road, S1 = south end of the x=200 road, etc.

EDGES: 24 directed lane edges (12 undirected road segments x 2 directions): 8 internal (4 links x 2) of length L_int = L_block - w_box = 193 m, and 16 stub edges of length L_ext = L_stub - w_box/2 = 146.5 m. Edges run from box edge to box edge. Edge id = 'from_to', e.g. 'W0_I00', 'I00_I10'. Stop line 2.0 m upstream of the box edge on every approach. Lane centre offset +/-1.75 m from the road axis; sign set by drive_side. Jam storage per edge = floor(L / (l_veh + s0)) = floor(193 / 6.5) = 29 vehicles internal, 22 per stub; these two numbers are the normalisers for every queue feature.

Plus 48 connector edges inside the boxes (12 per intersection = 4 approaches x 3 movements), ALL of length 7.0 m in v1 (arc radii are drawing-only).

DRIVING SIDE: drive_side in {'left', 'right'}, default 'left' (Indonesia). lateral_sign = -1 for left, +1 for right. The code and docs always say near-side turn (does not cross opposing traffic; = left turn under left-hand traffic) and far-side turn (crosses opposing traffic). Under right-hand traffic swap. Movement-to-exit table for approach travelling south (coming from the north arm): through -> south arm, near-side -> west arm under left-hand traffic (east under right-hand), far-side -> the other. The other three approaches by rotation. Right/left-turn-on-red is NOT allowed. No U-turns.

APPROACHES: named by compass arm the vehicle arrives from: N, E, S, W (phase k = that approach green). intersection_id x approach -> incoming edge lookup table; neighbour map: I00: E->I10, N->I01; I10: W->I00, N->I11; I01: S->I00, E->I11; I11: S->I01, W->I10 (two internal neighbours each, -1 otherwise).

MOVEMENTS AND CONFLICTS: all three movements T, NS, FS allowed from every approach. v1 phase plan = SPLIT PHASING: phase k in {N, E, S, W} releases all three connectors of approach k; nothing else is green. Static 12x12 per-intersection conflict matrix (identical for all four intersections): connector (k, m) conflicts with every connector of a different approach except the pair of near-side turns from opposite approaches and the pair {k-NS, opposite-T} that share no path; in v1 it is acceptable to mark every cross-approach pair as conflicting except (NS from k, NS from opposite(k)). The matrix is used only by the all-red clearance gate (green for approach j may start when no vehicle is on a connector that conflicts with any of j's three connectors) so that one vehicle stuck on a non-conflicting connector cannot freeze the intersection. Reference compatible sets for a future paired-phasing v2: {N-T, S-T, N-NS, S-NS}, {N-FS, S-FS}, {E-T, W-T, E-NS, W-NS}, {E-FS, W-FS}.

ENTRY / EXIT: the 8 boundary nodes are both sources (Poisson spawning onto the outbound stub edge) and infinite sinks (vehicles despawn when the rear bumper passes the boundary node, no blocking at exit). A vehicle may not spawn unless the first 10 m of the entry edge is empty and gap to the last vehicle >= s0 + v_spawn*T; otherwise it waits in a per-stub virtual entry queue that is logged every second and whose delay counts in that vehicle's total delay.

BOX RULES: a vehicle at the stop line may enter its connector iff (its approach is GREEN, or it is COMMITTED) AND the exit edge has free space >= l_veh + s0 + 1.0 m at its start. The free-space condition is anticipatory and colour-independent: whenever it fails for a vehicle's next movement, the stop line becomes that vehicle's virtual stationary leader from as far upstream as the leader lookup sees (100 m), so a vehicle approaching a blocked exit is already decelerating and can never become COMMITTED into a full exit. If an exit fills after commitment the vehicle enters anyway, follows its leader and may stop in the box (logged as box_blocked, expected rare). Inside a connector the leader is the last vehicle on the exit edge (gap = remaining connector length + its rear position), speed capped at v_turn for turns. Gridlock detector: no vehicle has crossed any stop line in the last 120 s while >= 10 vehicles are in the network -> gridlock = True, episode ends, flagged, kept in the dataset as a labelled failure.

DETECTORS (what the controller and later the twin can see, v1 = perfect truth, v2 = noisy): per approach edge a loop at the edge start (entry count), a loop at the stop line (exit count), and a camera zone covering the whole edge for queue counts (noise model in the twin section).


## vehicle_model

STATE PER VEHICLE: edge_id, s (metres from edge start, front bumper), v, a, status in {FREE, FOLLOWING, STOPPING, COMMITTED, IN_BOX, QUEUED_AT_ENTRY}, route (list of edge ids and movements), plus sampled parameters. 2-D (x, y) is derived only for logging and drawing: (x, y) = P_start + u*s + n*lateral_sign*1.75.

TIMESTEP: dt = 0.5 s physics (config; 0.1 s for a showcase run), 1 Hz logging, decisions every 5 s during green (see signal model). Plain Python loop over vehicle objects kept in one list per edge sorted by s descending; leader = previous element, or first vehicle on the next edge of the route (via the connector), or the stop line, whichever is nearest along the route within a 100 m horizon. Expected runtime 30-90 s per simulated hour; vectorise globally (one array per state variable) only if measured runtime exceeds 2 min.

CAR-FOLLOWING: Intelligent Driver Model (Treiber 2000).
  a_idm = a_max * [1 - (v/v0_local)^4 - (s_star/gap)^2]
  s_star = s0 + max(0, v*T + v*(v - v_leader) / (2*sqrt(a_max*b)))
  gap = bumper-to-bumper distance to the leader (stop line counts as a leader of length 0 and speed 0 at s_stop = L_edge - 2.0).
  Free road (no leader within 100 m, green ahead): a = a_max*(1 - (v/v0_local)^4).
Do NOT clamp the IDM term itself; after computing a: if a < -3.0 m/s^2 log hard_brake; then clip a >= -b_emerg (b_emerg = 7.0 m/s^2, the physical limit). No per-step acceleration noise in v1 (the per-vehicle parameter spread IS the student's "deviation").

INTEGRATION (ballistic, stop-exactly branch): if v + a*dt >= 0: s_new = s + v*dt + 0.5*a*dt^2, v_new = v + a*dt; else: s_new = s + v^2/(2*|a|), v_new = 0. Then per edge in order of s: if s_front_follower > s_rear_leader - 0.3: set s_front_follower = s_rear_leader - 0.3 and v_follower = min(v_follower, v_leader), log overlap_fixed (health metric, must stay below 1 per 10,000 vehicle-steps).

TURN SPEED (anticipatory cap, no hard-brake artefacts): for a vehicle whose next movement is a turn, v0_local = min(v0, v_limit, sqrt(v_turn^2 + 2*b*d_to_box)) evaluated from 60 m upstream, with v_turn = 5.0 m/s for both turn types; through movements v0_local = min(v0, v_limit). On the connector, v0_local = v_turn for turns.

STOP-OR-COMMIT (evaluated exactly once per vehicle at the instant its approach turns red, then latched): d = distance from front bumper to stop line, b_stop = 3.0 m/s^2 (comfortable-hard, ITE practice). If d >= v^2 / (2*b_stop): status = STOPPING (stop line becomes the virtual leader; IDM handles deceleration). Else: status = COMMITTED, the vehicle ignores the stop line, enters its connector and crosses; log red_commit with (d, v). Followers of a COMMITTED vehicle follow that vehicle, not the stop line. Only the first non-committed vehicle sees the stop line. Worst case with v0 capped at 1.15*v_limit = 16.0 m/s: commit distance 42.6 m, clearing time (42.6 + 7 + 4.5) / 16.0 = 3.4 s < 4.0 s minimum all-red; the conflict-clear gate covers the rest. IDM has no reaction time; do not add one (it destabilises IDM).

PARAMETER DISTRIBUTIONS (drawn once at spawn from the vehicle-params RNG stream; cars only in v1, vehicle_type column reserved):
  l_veh = 4.5 m fixed; s0 = 2.0 m fixed; b_emerg = 7.0 m/s^2 fixed.
  alpha ~ Beta(2, 2) on [0, 1] (latent driver aggressiveness, mean 0.5; stored in the vehicles table as a hidden ML target).
  v0    = v_limit * (1 + 0.20*(alpha - 0.5)) * LN(0, 0.08), clipped to [0.85, 1.15] * v_limit  (11.8 to 16.0 m/s at 50 km/h)
  a_max = 1.5 * (1 + 0.50*(alpha - 0.5)) * LN(0, 0.10), clipped to [0.8, 2.5] m/s^2
  b     = 2.0 * (1 + 0.30*(alpha - 0.5)) * LN(0, 0.10), clipped to [1.2, 3.0] m/s^2  (comfortable deceleration)
  T     = 1.2 * (1 - 0.40*(alpha - 0.5)) * LN(0, 0.10), clipped to [0.8, 1.8] s  (time headway; 1.2 not 1.5 so that IDM queue discharge lands near 1700-1900 veh/h/lane)
  LN(0, sigma) = lognormal multiplicative noise. v2 flag: vehicle classes car 0.85 (4.5 m), van 0.10 (6.0 m, a_max x0.8), bus 0.05 (12 m, a_max x0.6, T x1.3).
  Extra per-vehicle indicators logged (no extra physics): n_stops, total_wait_s, n_hard_brakes, n_red_commits, accel_energy = sum(a^2 dt).

SPAWN PROCESS: per physics step at each of the 8 entry stubs, spawn with probability p = lambda_e(t) * dt (dt = 0.5 s -> p <= 0.05; this is the correct non-homogeneous Poisson process). lambda_e(t) = lambda_base * asym_e * profile(t). lambda_base per episode drawn from the demand band (initial guess U(60, 250) veh/h per entry; stress band 250-320), to be RE-DERIVED from the measured saturation flow so that the busiest internal approach has v/c in {0.4 low, 0.7 design, 0.95 high} under fixed-time control. asym_e: 1.0 everywhere (symmetric) or NS entries x1.4 and EW entries x0.7 (asymmetric scenario). profile(t): flat = 1 in v1; peak = 1 + 0.6*exp(-((t - 1800)/600)^2) as the v2 one-liner. Spawn speed v_spawn = min(v0, v_leader if a leader is within 50 m else 0.8*v0); spawn requires the first 10 m free and gap >= s0 + v_spawn*T, else the vehicle waits in the entry queue (entry_queue_delay logged).

ROUTING / DESTINATIONS: destination ~ Categorical(OD[origin, :]) over the 7 other boundary nodes. Default OD row written relationally so it needs no mirroring: far end of own road 0.30; the two ends of the parallel road 0.15 each; the four ends of the crossing roads 0.10 each (sums to 1.00); od_pattern 'uniform' = 1/7 each as the second scenario. Route = Dijkstra on the 12-node directed graph with edge cost = length + turn penalty at the downstream node (T 0, NS +10 m, FS +25 m); ties broken uniformly from the routing RNG. Route stored as the list of (intersection, movement). Derived columns: route_len_m, n_intersections, n_turns, free_flow_time_s = sum(edge_len / min(v0, v_limit)) + n_turns * (7 / v_turn). Despawn at the boundary node; total_delay_s = entry_queue_delay_s + (travel_time_s - free_flow_time_s).

VALIDATION EXPERIMENTS (run before any dataset, figures in the report): (1) ring road 1 km, N = 10..150 vehicles: flow-density diagram must be triangular with jam density ~154 veh/km and capacity 1700-1900 veh/h; (2) 20-vehicle queue, green on: saturation headway = mean headway of vehicles 5-15 (target 1.9-2.2 s), start-up lost time ~2 s; record measured_sat_flow in the episodes table; (3) single intersection fixed-time, demand sweep: Webster-shaped delay curve, compare with Webster uniform delay d1 = C(1 - g/C)^2 / (2(1 - x g/C)) at x <= 0.7; (4) overlap_fixed rate and allred_extension histogram.


## signal_model

DISPLAY: every signal head shows exactly RED or GREEN; the dataset light columns are two-valued. The safety logic lives in the plant's internal states.

PLANT STATE PER INTERSECTION: phase in {0:N, 1:E, 2:S, 3:W} (the approach currently or most recently green), state in {GREEN, ALLRED}, time_in_phase_s (counted from green onset), time_in_allred_s, pending_phase, n_switches. Timing constants (config): t_min_green = 5 s, t_max_green = 60 s, t_allred_min = 4 s, decision_interval = 5 s.

PHASE TABLE (split phasing): phase k -> the three connectors of approach k are green; all other 9 connectors red. Unit test: for every phase, no pair of green connectors conflicts; never two approaches green.

SWITCH PROCEDURE: at a decision instant the controller returns requested_phase j in {0..3}.
  if j == phase: extend (always honoured; max-green rule below may override).
  elif time_in_phase < t_min_green: ignored, forced = min_green (cannot happen if decision instants are placed correctly; logged anyway).
  else: state <- ALLRED, pending_phase <- j, all approaches red. Green for j begins at the first t >= t_switch + t_allred_min such that no vehicle is on a connector conflicting with any of j's connectors (conflict-clear gate). Log allred_extension_s = actual - 4. Then phase <- j, time_in_phase <- 0.
  Requests arriving during ALLRED are ignored (forced = all_red).
MAX GREEN: if time_in_phase >= t_max_green AND any other approach has n_k > 0 (a conflicting call): forced switch to the other approach with the largest n_k (ties -> next in rotation N,E,S,W), forced = max_green. If no other approach has vehicles, hold (max green is a starvation guard, not a metronome).

DECISION INSTANTS (event-driven, per intersection, so every logged action is applicable): the first decision instant of a green is at green_onset + t_min_green; subsequent ones every 5 s while GREEN. No decisions during ALLRED. Every decision instant produces one signal_ticks row with action_requested, action_applied, forced code. This yields ~600-700 rows per intersection-hour.

HOW A CONTROLLER ACTS: controller.act(features_row) -> requested_phase (0..3). Baselines: fixed_time (rotation N,E,S,W with 20 s green each -> cycle 4*(20+4) = 96 s; the controller returns 'next' when time_in_phase >= 20, else current); max_pressure (see ML section, pure function of the row); longest_queue (switch to argmax n_k if n_best > n_current + 3); random_dwell (hold a random duration U(5, 40) s then switch to a random other approach; used only for dataset coverage); ml (model wrapper). The plant, not the controller, enforces min/max green and clearance, so every controller is safe by construction and directly comparable.

STOP-LINE BEHAVIOUR: at the instant an approach turns red every vehicle on it is evaluated once with the stop/commit rule (vehicle model); STOPPING vehicles treat the stop line as a stationary leader; COMMITTED vehicles finish crossing during ALLRED. On green the first vehicle's leader becomes the last vehicle on its exit edge (via the connector), so queue discharge and spillback are ordinary car-following.

SAFETY INVARIANTS (pytest, every episode): (1) never two approaches green; (2) at every green onset no vehicle is on a conflicting connector (box_clear_violations == 0); (3) no vehicle crosses a stop line on red unless COMMITTED (red_violations == 0); (4) min green never violated; (5) all-red duration >= 4 s; (6) vehicle conservation: spawned = arrived + in_network + entry_queued. Reported per episode: n_red_commits (expected 0.5-2 per phase end on saturated approaches; this is a modelling consequence of two-colour signals, documented as a KPI, not a bug), allred_extension distribution, n_box_blocked, lost_time_s = sum of all-red durations.

LOST TIME FOR WEBSTER / CAPACITY: per phase l = start-up lost time (2 s, measured) + 4 s all-red = 6 s; L = 24 s per cycle. Approach capacity under fixed-time ~ measured_sat_flow * g_eff / C, e.g. 1800 * 20/96 = 375 veh/h; demand band is derived from this measured number, never from the textbook 1800.


## dataset

FORMAT AND LAYOUT: Parquet (pyarrow, zstd) for everything plus a CSV copy of episodes, vehicles and signal_ticks for the course hand-in (signal_ticks is ~300k rows, fine as CSV). Folder: data/traffic_v1/{episodes.parquet, vehicles.parquet, signal_ticks.parquet, vehicle_states/episode_{id}.parquet (showcase episodes only), network_edges.csv, data_dictionary.csv, feature_sets.json, DATACARD.md, config.json}. Every table carries episode_id; episodes carries seed and config_hash so every row is regenerable from (generator_version, config, seed).

GRAIN: three generated tables (one row per episode / per vehicle / per intersection-decision-instant) plus one 1 Hz trajectory table for a handful of showcase episodes. link-level statistics are a pandas groupby over vehicle_states, which is itself a graded DS skill.

TABLE episodes (1 row per episode; PK episode_id):
  episode_id int32; seed int64; config_hash str; generator_version str; created_at timestamp;
  drive_side str; lanes_per_dir int8; L_block_m float; v_limit_mps float; dt_s float (0.5); duration_s int (3600); warmup_s int (300); cooldown_s int (300, spawning off); decision_interval_s (5); min_green_s (5); max_green_s (60); allred_min_s (4);
  demand_level str {low, design, high, stress}; lambda_base_vph float (per entry); demand_asym str {sym, ns_heavy}; demand_profile str {flat, peak}; od_pattern str {default, uniform};
  controller str {fixed_time, max_pressure, max_pressure_eps, random_dwell, ml_v1}; controller_eps float; sensor_noise_level float {0, 0.05, 0.15}; log_trajectories bool; split str {train, val, test, test_ood};
  KPIs: n_spawned, n_arrived, n_in_network_end, n_entry_queued_max int; throughput_vph float; mean_total_delay_s, p90_total_delay_s float (over vehicles spawned after warm-up, unfinished vehicles count their delay so far); mean_stops float; max_queue_veh int; switches_per_min float; n_red_commits, n_hard_brakes, n_overlap_fixed, n_box_blocked int; allred_extension_mean_s float; gridlock bool; gridlock_t float; measured_sat_flow_vphpl float (from the validation run under this config); label_switch_rate float (share of decision rows where y_mp_action != phase).

TABLE vehicles (1 row per spawned vehicle; PK (episode_id, veh_id)):
  episode_id, veh_id int32; spawn_request_t, enter_t, exit_t float (NaN if unfinished); completed bool; is_warmup bool (spawn_request_t < warmup_s; excluded from KPIs and labels);
  origin, destination str (W0..N1); route_movements str (e.g. 'I00:T|I10:FS|I11:NS'); route_edges str; route_len_m float; n_intersections, n_turns int8;
  free_flow_time_s, travel_time_s, entry_queue_delay_s, total_delay_s float (= entry_queue_delay_s + travel_time_s - free_flow_time_s); total_wait_s float (time with v < 2 m/s); n_stops int8 (transitions v > 2 -> v < 0.5); n_red_commits, n_hard_brakes int8; accel_energy float;
  hidden parameters: alpha, v0_mps, a_max_mps2, b_comf_mps2, T_headway_s float; vehicle_type str ('car').

TABLE signal_ticks (MAIN ML TABLE; 1 row per intersection per decision instant; PK (episode_id, intersection_id, t)). Column-namespace rule: plain names = observable state features; obs_* = sensor-realistic copies; down_* / nb_* = downstream and neighbour features (observable through the controller network); oracle_* = label-function internals (never features); action_* = what happened; y_* / reward_* = targets. Windows are trailing only.
  keys/time: episode_id int32; intersection_id int8 (0..3); t float; tick_idx int32; is_warmup bool (t < 300); is_tail bool (t > duration - 30; regression labels null).
  signal: phase int8 (0..3); time_in_phase_s float; time_since_switch_s float; max_green_remaining_s float; n_switches int16.
  per approach a in {N,E,S,W} (4 each): q_a int16 (vehicles with v < 2 m/s on the whole approach edge); n_a int16 (all vehicles on the approach edge); arr_a_30s int16 (vehicles that entered the edge in (t-30, t]); dep_a_30s int16 (stop-line crossings in (t-30, t]); wait_max_a float (longest current wait on the approach, s); head_dist_a float (distance of the first vehicle to the stop line, -1 if empty); spill_a bool (last vehicle's rear within 2 m of the edge start).
  downstream per outgoing direction d in {N,E,S,W}: down_n_d int16 (vehicles on the outgoing edge toward d; 0 for a boundary stub); down_occ_d float (down_n_d / storage of that edge); down_blocked_d bool (free space at its start < l_veh + s0 + 1).
  aggregates: q_total, n_total int16; wait_sum_total float; throughput_cum int32.
  neighbour per direction d: nb_d_exists bool; nb_d_phase int8 (-1 if none); nb_d_green_toward_me bool (the neighbour's current green approach feeds the link toward me); nb_d_time_in_phase_s float (-1); nb_d_n_to_me int16 (vehicles on the link from that neighbour toward me, -1).
  sensor copies (4): obs_q_a int16 = Binomial(q_a, 1 - p_miss) + Poisson(p_miss/2), p_miss = sensor_noise_level; identical to q_a when noise is 0.
  oracle internals: oracle_pressure_a float (4) = n_a - (sum of down_n over the three exit directions of approach a) / 3, set to -1e9 if down_blocked for a's through exit; oracle_forced int8.
  actions: action_requested int8; action_applied int8 (phase in force after the plant's filter); forced int8 {0 none, 1 min_green, 2 max_green, 3 all_red}; switched bool (action_applied != phase).
  labels: y_mp_action int8 (max-pressure decision computed on EVERY row regardless of the driving controller; pure function of the row's own columns, unit-tested as such); y_q_total_t30 int16 (q_total 30 s later; NaN in tail); y_delay_next_30s float (wait increments on the 4 approach edges in (t, t+30]); y_throughput_next_30s int16; y_gridlock_300s bool; reward_queue float = -(q_total at the next decision instant); reward_wait float = -(wait_sum_total(next) - wait_sum_total(now)); done bool.
  twin hooks: source str ('sim' offline; 'physical' / 'twin' later).
  ~75 columns. Max-pressure label rule (also the baseline controller): if time_in_phase < 5 -> keep; else best = argmax_a oracle_pressure_a; y = best if oracle_pressure_best > oracle_pressure_phase + 2 (hysteresis, vehicles) else phase; if time_in_phase >= 60 and any other n_a > 0 -> argmax over the other approaches.

TABLE vehicle_states (1 Hz, only for episodes with log_trajectories = True, ~5 episodes chosen one per demand level; ~600k rows each): episode_id, t, veh_id, edge_id, s_m, x_m, y_m, v_mps, a_mps2, leader_id, gap_m, dist_to_stopline_m, signal_ahead {G, R, AR}, status, cum_wait_s. Used for the viewer, the fundamental-diagram plot, link-level groupbys and twin replay.

STATIC: network_edges.csv (edge_id, from_node, to_node, heading, length_m, storage_veh, is_stub, approach_dir_at_dest, intersection_id_at_dest).

VOLUME AND DESIGN: v1 = 120 episodes x 4200 s (300 warm-up + 3600 + 300 cool-down); develop on 10. Rows: signal_ticks ~120 x 4 x 650 = ~310k; vehicles ~120 x 3000 = ~360k; episodes 120; vehicle_states 5 x ~600k. Scenario mix per episode (stratified random draw): demand_level {low 25%, design 40%, high 25%, stress 10%} with lambda_base jittered U(0.9, 1.1) x level; demand_asym {sym 50%, ns_heavy 50%}; od_pattern {default 70%, uniform 30%}; controller {max_pressure 40%, max_pressure_eps (eps 0.3: with prob 0.3 the requested phase is random) 30%, fixed_time 20%, random_dwell 10%}; sensor_noise_level {0 60%, 0.05 25%, 0.15 15%}. Rationale for the mixture: a single deterministic policy gives no counterfactual actions and a learned controller can only copy it; random-dwell and eps episodes supply long queues, spillback and both actions from similar states. Generation time: ~1-2 min per episode in plain Python -> 2-4 h unattended.

SEEDS: seed = 100000 + episode_id; SeedSequence(seed).spawn(3) -> rng_demand (arrivals, OD, routing ties), rng_vehicles (parameters), rng_controller (eps, random dwell). Common random numbers: two controllers on the same seed face identical arrivals and drivers, which is what makes paired comparisons meaningful. Determinism test: run twice, hash of vehicles table equal.

SPLITS: assigned per episode in episodes.split: 70/15/15 train/val/test stratified by (demand_level, controller); ALL stress-level episodes -> test_ood (never trained on); random_dwell episodes eligible for train only (eval on realistic states). Training code uses GroupKFold(groups = episode_id). Never a row-wise random split: consecutive rows 5 s apart are near-duplicates and a row split gives ~0.99 accuracy that collapses in closed loop.

DATA DICTIONARY CONVENTIONS: data_dictionary.csv with (table, column, dtype, unit, description, namespace in {key, time, signal, state, sensor, downstream, neighbour, oracle, action, label, rl, twin}, twin_observable bool, leaky_for in {'', imitation, regression, all}, null_policy, example). Integers smallest safe width, floats float32, -1 sentinel for "none" in int columns, NaN only in float label columns. feature_sets.json: 'imitation_truth' = signal + per-approach + down_* + nb_* columns; 'imitation_sensor' = same with obs_q_a replacing q_a and without n_a/arr_a/dep_a/head_dist_a/wait_max_a; 'regression' = imitation_truth + action_applied. DATACARD.md: generating process, parameter distributions, measured saturation flow and validation figures, label balance per controller, KPI distributions, known limitations (Poisson arrivals, IDM drivers, no pedestrians, no amber, no lane changes, conflict-free split phasing, red commits as a modelling consequence).

LEAKAGE PITFALLS (enforced): (1) oracle_pressure_* and y_* never appear in a feature set (a model given oracle_pressure_* learns a one-line rule); (2) no column depends on state after t except y_*, reward_*; all windows are (t - w, t]; (3) action_applied is a feature only for regression / lookahead, never for imitation; (4) is_warmup rows excluded from training and evaluation, is_tail rows have null regression labels; (5) split by episode, OOD family held out; (6) regression targets are "under the logged policy" (future actions of the driving controller affect them), stated in the data card; (7) intersection_id is not a feature (nb_*_exists already encodes the corner); (8) no time-of-day / t_frac feature (it lets the model memorise the demand schedule and does not transfer to the twin); (9) unit test: recompute y_mp_action from the row's own columns == stored; perturb-the-future test on one episode shows no feature column changes.


## ml_models

THE "MODEL FOR ALL THE TRAFFIC LIGHTS" is ONE shared model, applied independently at each of the four intersections through the same observe(intersection) -> feature row interface, with neighbour and downstream columns giving it the coupling information. The ladder below is ordered so that each rung is a complete, reportable deliverable; the course deliverable is rungs 0-1 plus the evaluation protocol.

RUNG 0 - NON-ML BASELINES (week 2; ~10-20 lines each):
  fixed_time: rotation N,E,S,W, 20 s green each (cycle 96 s). Optional Webster split: C = (1.5*L + 5)/(1 - Y) with L = 24 s, Y = sum over phases of (approach flow / measured saturation flow), clipped to [60, 150] s, greens proportional to flow ratio.
  longest_queue: switch to argmax n_a if n_best > n_current + 3.
  max_pressure (the bar to beat): pressure_a = n_a - mean(down_n over a's three exits), skip blocked exits, hysteresis 2 vehicles, min/max green enforced by the plant. Describe it honestly as "a strong parameter-light heuristic, throughput-optimal under idealised assumptions (unbounded storage, no spillback) that this network violates", not as "provably optimal".

RUNG 1 - SUPERVISED TABULAR MODELS ON signal_ticks (the course deliverable, week 4):
  Task A, imitation (4-class): predict y_mp_action from feature set 'imitation_sensor' (obs_q_a, phase, time_in_phase_s, max_green_remaining_s, down_occ_d, down_blocked_d, nb_* columns) and separately from 'imitation_truth'. Models: LogisticRegression(class_weight='balanced') as interpretable baseline; sklearn HistGradientBoostingClassifier(max_iter=400, learning_rate=0.05, max_depth=6, l2_regularization=1.0, early_stopping=True, class_weight='balanced') as the main model; optional DecisionTreeClassifier(max_depth=5) to show the recovered rule. CV = GroupKFold(5, groups=episode_id); metrics: balanced accuracy, macro F1, F1 of "switch" (rows where label != phase, ~15-30% base rate), confusion matrix, permutation importance. Expected: ~99% on truth features (a tautology, present it as a sanity check), 85-95% on noisy sensor features (the interesting number: how much control quality is lost through realistic sensing).
  Task B, regression: predict y_q_total_t30 and y_delay_next_30s from 'regression' features (includes action_applied). Models: Ridge baseline, HistGradientBoostingRegressor(max_iter=500, learning_rate=0.05, max_depth=8). Metrics MAE, RMSE, R^2 via GroupKFold; report the partial dependence on action_applied (the control-relevant effect size), not only R^2 (queue at t+30 is mostly explained by queue at t).
  Task C (optional, 20 lines): classify y_gridlock_300s (early-warning), PR-AUC, by demand level.
  CLOSED-LOOP DEPLOYMENT (the metric that matters): MLController.act(row) = model.predict_proba -> requested phase = argmax, with hysteresis: switch only if P(best) > P(current) + 0.1; one model.predict call batched over the 4 intersections per decision tick; the plant enforces safety. Run on 5 held-out paired seeds x 3 demand levels (low, design, high = unseen) vs fixed_time and max_pressure.

RUNG 2 - LOOKAHEAD POLICY FROM THE REGRESSOR (stretch, 1 day): a* = argmin over the 4 candidate actions of f(s, a) predicted delay_next_30s, with a switching margin of 0.5 s of delay. State explicitly that f estimates outcomes under the logged (noisy max-pressure / random) policy, so this is one step of policy improvement over the behaviour mixture, not model-predictive control. One optional re-collection round: deploy ml_v1 with eps = 0.1 for 20 episodes, relabel with max-pressure, retrain on the union, report closed-loop delay before/after.

RUNG 3 - REINFORCEMENT LEARNING (after the course deliverable, only if the simulator runs a 3600 s episode in <= 60 s):
  Env: gymnasium-style step(actions[4]) advancing the world to the next decision instants; because decision instants are per-intersection event-driven, implement as "advance until the next intersection needs a decision" and return that intersection's (obs, reward) (one transition per intersection decision), or synchronise all four on a 5 s grid for simplicity in v1.
  STATE (per intersection, 37 floats in [0,1], identical columns to signal_ticks): phase one-hot (4); time_in_phase/60; q_a/29 (4); n_a/29 (4); arr_a_30s/20 (4); down_occ_d (4); per direction d: nb_d_exists, nb_d_green_toward_me, nb_d_time_in_phase/60, nb_d_n_to_me/29 (16). No t_frac.
  ACTION: Discrete(4) = requested approach; infeasible actions (switch during min green) masked in both action selection and the bootstrap target, or the agent is simply not asked on those ticks.
  REWARD: r = -q_total/29 - 0.05 * switched (whole-edge queues, never a 100 m zone, so queues cannot be hidden); ablation: pressure reward -|sum n_a - sum down_n|/29. Gridlock: r = -10 and terminate. gamma = 0.95 (effective horizon ~100 s). Never throughput alone (starves minor approaches).
  Algorithm: EITHER Stable-Baselines3 DQN on a centralised joint action Discrete(256) with the four observation rows concatenated (148 dims; pure single-agent, works out of the box) OR a parameter-shared DQN where the four intersections are four parallel envs over one shared World (SB3 VecEnv trick). Hyperparameters: MLP 64-64, Adam 5e-4, batch 64, replay 30k transitions (small: large buffers store stale multi-agent dynamics), target update 500 steps, Huber loss, epsilon 1.0 -> 0.05 over 60 episodes, 150 training episodes on design + ns_heavy demand, 3 training seeds. Expected: ties max-pressure on trained demand, loses on unseen; a clean report of that is the result.

EVALUATION PROTOCOL (fixed before training anything): controllers {fixed_time, longest_queue, max_pressure, ml_v1 (sensor features), ml_v1 (truth features), optional lookahead, optional DQN} x scenarios {low, design, high (unseen), ns_heavy} x 5 paired evaluation seeds (1000..1004, identical arrivals and drivers for every controller via the demand/vehicle RNG streams). Metrics per episode: mean_total_delay_s (primary, includes entry-queue delay and unfinished vehicles' delay so far), p90_total_delay_s, throughput_vph, completion_rate, max_queue, switches_per_min (flag < 0.7 never-switching and > 3.5 flicker), n_red_commits, gridlock flag (never excluded; reported as a rate). Report paired mean difference vs max_pressure +/- 1.96 SE over seeds in one table; a Wilcoxon signed-rank test is an optional scipy one-liner. Offline accuracy/R^2 appears only as a model diagnostic next to the closed-loop table, to show that the two rank models differently. Fraction of decision steps with any feature outside its training range ("OOD rate") reported per controller.

COURSE DELIVERABLE vs LATER: the course notebook = data card + EDA (delay vs demand curve, fundamental diagram, label balance, feature-label correlations, driver alpha vs delay) + Task A and Task B with GroupKFold + closed-loop comparison table. Later: lookahead policy, re-collection round, RL, twin-aware evaluation (policy trained on truth evaluated on twin-estimated features to quantify the twin-induced gap).


## digital_twin

WHAT "DIGITAL TWIN" MEANS HERE (and what v1 is not): v1 is a simulation model, the first component of a twin. A twin = model + live data link + synchronisation/calibration loop. The extension adds the other two using a twin-of-a-sim architecture, which is the standard way to study twins when no real road exists and has the advantage that ground truth is available for evaluating fidelity. Five separable boxes, each a module: P = physical system (hidden truth), S = sensing channel (partial, noisy, delayed), T = twin (model + state estimator kept in sync using only S), C = controller (reads T's estimate only, commands flow back to P), M = monitor (twin-vs-physical drift, triggers resynchronisation). The twin exists only if C never reads P's truth and T can be wrong. Enforced by a unit test that modules defining act() never import the simulator's truth accessors (the offline labeller and any RL env live in a separate train/ module that is allowed to).

TOOLING CHOICE: custom Python simulator (chosen) vs SUMO/TraCI vs CityFlow.
  Custom numpy/Python: + the dataset is the student's own physics (the assignment's point); deepcopy(sim) gives checkpoint/branch for free; deterministic from (config, seed); two instances cost nothing; red/green-only signals and split phasing are trivial to express; pip-only. - no external validation (mitigated by the fundamental-diagram, saturation-flow and Webster checks); routing, box rules and detectors must be written (~700-1000 lines total).
  SUMO + TraCI: + validated physics, lanes, detectors (E1/E2), netgenerate --grid --grid.x-number=2 --grid.y-number=2 --grid.length=200 --grid.attach-length=150 builds the "#" in one command. - install and API learning cost 1-2 weeks, 10-100x slower per Python step, loses the "my own synthetic data" story, two-colour signals are awkward. Verdict: not the main tool; the natural "physical" backend for the twin extension if the grader asks "is your simulator realistic?", and a one-scenario validation appendix (compare delay distributions).
  CityFlow / Flow: fast and RL-oriented but painful source builds, fixed per-flow car parameters (cannot express per-car distributions), no detector/noise layer, stale maintenance. Rejected.

ARCHITECTURE (lockstep, single process; latency modelled in simulation time; asynchronous processes are future work, not code):
  P: World(seed_phys) with hidden per-car parameters (and, in level 2, hidden perturbed population means and demand); DetectorBank(rng_sensor) producing SensorFrame(t_meas, readings) with: entry loop and stop-line loop per approach edge (counts per 1 s, p_miss = 0.03, p_double = 0.01), camera queue count per approach (round(q + N(0, 1)), clipped >= 0, p_drop = 0.02 per frame), fixed delivery delay 1 s (frames delivered when t >= t_meas + 1), fault scenarios frozen_detector(det_id, t0 = 1800, dur = 60) and dead_detector. PhaseReport every 1 s (actual phases; actuation delay U(0.2, 0.5) s, p_fail = 0.005 so the twin's assumed phase can be wrong).
  T (level A, the committed deliverable): per approach edge, n_link estimate by conservation n_hat += entry_count - exit_count (exactly the quantity the two loops bound; reset to the camera count when the edge is observed empty), and queue_est = min(EMA_0.5(camera_q), n_hat); innovation check: if |camera_q - queue_pred| / sqrt(P + R) > 3 for 5 consecutive frames, or the camera value is unchanged for 15 frames while loops count > 0, declare the detector stuck, set its weight to zero (coast on loops) and log the event. Twin phase state is overwritten from PhaseReport. Twin output = the same signal_ticks feature row via the same build_features() used offline, with source = 'twin'.
  T (level B, optional): a replica World that spawns vehicles at entry-loop detections with population-mean parameters, removes them at exit-loop events, is nudged every 5 s toward queue_est (insert/remove stopped vehicles at the queue tail when the difference >= 2), and supports what-if branching: copy.deepcopy(replica), roll 30 s under each candidate phase, return predicted queue sums (this is exactly the counterfactual machinery, reused online).
  C: any controller from the ladder, called with the twin's row; commands carry apply_at = t and go through the actuation queue.
  M: per intersection per 1 s: queue_mae_truth = mean over approaches |queue_est - q_true| (evaluation drift, possible only because P is a simulator), pred_err_30s = |queue predicted 30 s ago - camera now| (operational drift a real twin can compute), phase_mismatch. Thresholds: soft 2 veh -> nudge, hard 4 veh sustained 30 s -> hard resync (rebuild lane contents from observations), phase mismatch 3 s -> adopt reported phase, log 'actuation_divergence'. Logged to twin_drift(episode_id, t, intersection_id, metric, twin_value, physical_value, action).
  Twin KPIs: fidelity (mean queue_mae_truth, target <= 1.5 veh at design demand), data age at decision = t - max(t_meas incorporated) (target <= 1.5 s), resync rate (< 6 per hour), prediction MAE at 5 s and 30 s horizons vs synchronisation interval, and the controller performance gap: the same policy driven by truth features vs twin features.

HOW THE TABULAR DATASET FEEDS THE TWIN: (1) the same build_features() turns either simulator state or estimator state into the signal_ticks row, so a model trained offline on signal_ticks is deployed on the twin with zero schema change (train/serve skew eliminated by construction); (2) obs_q_a and sensor_noise_level in v1 already train models on sensor-like inputs; (3) the source column distinguishes sim / physical / twin rows so twin-vs-physical comparisons are a groupby; (4) vehicle_states of a showcase episode is the input for twin level 0: replay logged rows into the estimator, compare estimates with logged truth, no new simulation code; (5) deepcopy checkpoint/branch, already needed for optional counterfactual labels, is the twin's what-if engine; (6) episodes.seed plus common random numbers let the twin's "physical" episode be regenerated exactly for debugging.

ROADMAP: Level 0 (2 days, after the dataset): offline replay twin on a showcase episode, drift plot, one table of fidelity numbers. Level 1 (1 week): lockstep loop with DetectorBank + level-A estimator + PhaseReport, frozen-camera demo (t = 1800 s, 60 s: estimate diverges, stuck-sensor rule fires, estimate reconverges within 20 s of recovery), controller comparison on twin features, two-panel matplotlib animation (truth left, estimate right, drift strip below). Level 2 (1 week): "reality" = P with hidden perturbed population (T mean 1.0 instead of 1.2, a_max mean 1.2, demand +20%, detector dropout 10%); twin recalibrates per-entry arrival rates by exponential smoothing of entry-loop counts every 60 s; report 60 s-ahead queue prediction error vs sync interval and a controller tuned on the twin deployed on reality. Level 3 (future work paragraph only): asynchronous processes with a timestamp-aligned transport, SUMO as the physical side, replica microsim with nudging, LED hardware mirror.

- LANES: dataset-schema and ML lenses wanted 2 lanes per direction (lane fixed at entry, per-lane queue columns); simulation-physics, skeptic and both critiques showed that without lane changes a queued far-side turner blocks the inner lane for the whole green and that lane choice by 'next movement' strands vehicles whose turn is two nodes away. Resolved: 1 lane per direction in v1 with lanes_per_dir as config; per-lane columns dropped; the student confirms the reading of '4 ways' before coding.
- PHASING AND LEFT TURNS: ML and twin lenses proposed 2-phase with far-side turns banned; the ML critique enumerated that this drops 24 of 56 OD pairs and creates clockwise loop routes. Dataset lens proposed 2-phase permissive lefts; its critique showed the head left-turner blocks lane 0 for the entire green under saturated opposing flow. Simulation lens proposed split phasing. Resolved: split phasing (4 actions, all movements, no yielding logic, every destination reachable); paired phasing kept as v2 with the conflict matrix already written.
- ALL-RED LENGTH AND THE STOP/COMMIT DECELERATION: proposals ranged from 2 s (dataset, ML, twin lenses) to 3 s + guard (simulation) to 5 s intergreen (skeptic), with commit rules using b_emerg (4.5-6 m/s^2), b_comf (3 m/s^2) or a 'decision braking' 4.5 m/s^2 plus reaction time. Critiques showed 2 s is unsafe for any committed vehicle and that IDM has no reaction time. Resolved: commit rule uses b_stop = 3.0 m/s^2 with no reaction time, evaluated once and latched; v0 capped at 1.15 v_limit; all-red minimum 4 s plus a conflict-matrix clearance gate and a 'box clear at green onset' invariant, so safety holds by construction rather than by tuning.
- BOX-EMPTY GUARD VS CONFLICT MATRIX AND DON'T-BLOCK-THE-BOX: the simulation lens's three rules (commit, exit-space check at the stop line, box-empty guard) contradicted each other (a committed car can be denied at a line it cannot stop at; one stuck car freezes all phases). - DECISION TIMING: the simulation lens's fixed 5 s control tick with 5 s min green made one action per cycle a silent no-op (effective min green 7 s); the dataset lens's absolute 5 s grid skipped ticks during all-red. Resolved: per-intersection event-driven decision instants at green_onset + min_green and every 5 s thereafter, so every logged action is applicable; max green forces a switch only when a conflicting call exists.
- CAR-FOLLOWING DT AND CLAMPING: simulation lens insisted on dt = 0.1 s and 'IDM needs dt <= 0.2'; critiques cited Treiber and Kanagaraj (2015) for ballistic stability up to 0.5-1.0 s. Dataset and twin lenses clamped IDM at -b_emergency and still asserted gap >= 0; critiques showed clamping destroys IDM's collision-free property. Resolved: dt = 0.5 s ballistic with the stop-exactly branch, no clamp inside IDM, hard_brake logged below -3 m/s^2, physical clip at -7 m/s^2, and a post-step overlap guard whose counter is a health metric rather than an assertion.
- SATURATION FLOW AND DEMAND BAND: simulation lens derived 1760 veh/h from the Newell headway formula and sized demand at U(100, 400) veh/h per entry; its critique showed IDM's equilibrium gap gives ~1500 at T = 1.5 s so that band is already saturated; ML critique made the same point about Webster's 1800. Resolved: T mean lowered to 1.2 s, saturation flow MEASURED in the 20-vehicle discharge test, and the demand band derived from the measured value targeting v/c 0.4 / 0.7 / 0.95 on the busiest internal approach.
- DATASET BREADTH: dataset lens specified ~175 columns, five tables, counterfactual branching labels, offline-RL columns, LHS scenario design and 300 episodes; its critique showed the branching cost was ~220% not 60%, the stratification was impossible, and most columns were unusable. ML lens wanted tick logs for all 50 episodes; skeptic wanted 300 runs plus DAgger rounds. Resolved: three generated tables, ~75 columns in signal_ticks, 120 episodes, trajectories for 5 showcase episodes, no counterfactual labels (the regressor plus lookahead gives the 'which action was better' story), one optional re-collection round.

# COMPLETENESS CHECK (corrections that override the synthesis)


## verdict

The synthesis is a strong, mostly correct design: it fixes the student's reversed order of work, resolves the red/green-only problem with a real plant (all-red + min/max green + stop-or-commit + clearance gate), chooses split phasing so every destination is reachable with a 4-action space, specifies a genuinely twin-ready schema, and is honest about what ML can achieve against max-pressure. Before coding, five things must be corrected because they would silently corrupt data or break the safety invariants: the near-side/far-side exit table is backwards under left-hand traffic (arena); the stop-or-commit rule has no case for followers of committed vehicles or for vehicles arriving after red onset, which produces red violations as written (vehicle model); v0_local = min(v0, v_limit) nullifies half of the speed distribution and the quoted worst case (vehicle model); the 30 s-ahead labels and rewards need a 1 Hz per-intersection aggregate log that does not exist for 115 of the 120 episodes (dataset); and throughput_cum / n_switches are clock proxies inside the very feature sets whose leakage rules forbid clocks. Smaller factual slips (g_eff = 18 s not 20 s, t-interval with 5 seeds, Wilcoxon impossible at n = 5, SB3 DQN has no action masking, IDM is not triangular) are easy to fix in the text. The bigger risk is scope: the build plan sums to 66 h in a 60 h window with no slack, and the simulator, 75-column schema, test regime and evaluation harness are each individually reasonable but collectively 2-3x what one intro-DS student will finish; the design should be shipped with the cuts listed above as the default v1 (box-empty gate, one driving side, ~35 columns, 3-controller closed loop, twin level 0 only) and the full version kept as the documented extension path.


## missing

- VEHICLE MODEL / STOP-OR-COMMIT: the rule is only defined for vehicles present at the instant of red onset, and 'followers of a COMMITTED vehicle follow that vehicle, not the stop line'. Two cases are undefined: (a) a vehicle that enters the approach edge after red onset is never evaluated (needs a default STOPPING with the stop line as leader); (b) a follower of a committed vehicle, once that vehicle crosses the line, is handed the stop line as leader with no evaluation. Example: follower at 13.9 m/s at IDM equilibrium gap (~19 m) behind a leader that committed at d=30 m is at d~14 m when the leader clears, needs 32 m to stop at 3 m/s^2, so IDM gives a ~ -7 m/s^2 and it still crosses on red, breaking safety invariant (3) red_violations == 0. Fix: at red onset evaluate every vehicle on the edge in order from the stop line, each gets its own STOPPING/COMMITTED latch against its own d and v (committed chains are allowed), anything arriving later defaults to STOPPING.
- DATASET LABELS: y_q_total_t30, y_delay_next_30s, y_throughput_next_30s, reward_queue and reward_wait need the intersection state at non-decision times (t+30 s, next decision instant) for all 120 episodes, but 1 Hz state (vehicle_states) exists only for 5 showcase episodes and signal_ticks rows are 5 s apart with gaps during all-red. A lightweight per-intersection 1 Hz aggregate log (q_total, wait_sum_total, stop-line crossings) must be written in every episode, and the label post-pass must be specified against it.
- TIME AXIS / FLAGS: episodes have 300 s warm-up + 3600 s + 300 s cool-down, but 'duration_s = 3600' and 'is_tail = t > duration - 30' are ambiguous about whether t=0 is warm-up start (then is_tail falls mid-run at 3570 s) or main-period start. There is no is_cooldown flag: cool-down rows (spawning off, queues draining) are a different feature distribution and the text never says whether they are trained on, evaluated on, or used for KPIs. Also 300 s warm-up is ~3 fixed-time cycles; at high demand queues have not reached steady state, so either justify or check with a q_total-vs-t plot.
- REPRODUCIBILITY DETAILS: SeedSequence spawns only 3 streams (demand, vehicles, controller) but obs_q_a sensor noise needs its own rng_sensor (the twin section mentions one; the dataset section does not). Common random numbers only hold if destination and vehicle parameters are drawn at spawn REQUEST time (not entry time) and the per-entry draw order per step is fixed; this is never stated. Library versions (sklearn >= 1.2 is required for HistGradientBoostingClassifier(class_weight=...); HGB results differ by version) should be recorded in config.json / DATACARD.md alongside generator_version.
- CLOSED-LOOP EVALUATION PROTOCOL: the sensor_noise_level used when ml_v1 (sensor features) runs closed loop is unspecified, and the live loop must then run the obs_q_a noise generator inside the simulator, which is not in any module list. Replace with a plain threshold (e.g. |diff| >= 3 veh for 5 consecutive frames). The conservation estimate n_hat drifts without bound under p_miss / p_double because it is only re-anchored 'when the edge is observed empty', which at design demand may never happen on internal links; add periodic re-anchoring to the camera count.
- OPEN DECISIONS: the student's phrase 'the ML model for all the traffic lights' also reads as ONE centralised model with four outputs (one row per synchronised 5 s tick with 4 x per-intersection features and 4 labels, exactly what the RL rung does with its 148-dim state). ## wrong

- CLAIM: ARENA, movement-to-exit table: 'for approach travelling south (coming from the north arm): near-side -> west arm under left-hand traffic (east under right-hand)'.
  FIX: Backwards. Facing south, left is EAST (rotate heading (0,-1) by +90 deg -> (1,0)). Under left-hand traffic the near-side turn is a left turn, so a southbound vehicle exits to the EAST arm; west is the far-side (right) turn. The table as written is the right-hand-traffic answer labelled as left-hand. Since the synthesis itself warns that 'mixing conventions silently corrupts every turn table', derive the exits programmatically: near-side exit heading = inbound heading rotated 90 deg toward drive_side (+90 CCW for left, -90 for right), far-side = the opposite rotation, and unit-test it.
- CLAIM: SIGNAL MODEL, lost time: 'Approach capacity under fixed-time ~ measured_sat_flow * g_eff / C, e.g. 1800 * 20/96 = 375 veh/h' with l = 6 s per phase.
  FIX: Effective green = displayed green + intergreen - lost time = 20 + 4 - 6 = 18 s, so capacity = 1800 * 18/96 = 337 veh/h. The text uses the displayed green while calling it g_eff; the v/c calibration and Webster Y must use 18 s (or 20 + allred_mean - l if all-red extends).
- CLAIM: VEHICLE MODEL, stop-or-commit: 'Worst case with v0 capped at 1.15*v_limit = 16.0 m/s: commit distance 42.6 m, clearing time 3.4 s < 4.0 s minimum all-red'.
  FIX: The fast vehicle is not the worst case. Clearing time at constant speed is t(v) = v/(2*b_stop) + (7 + 4.5)/v, minimised (~3.1 s) near v = 5.9 m/s and exceeding 4 s for v below ~3.2 m/s: a creeping vehicle at 2 m/s that commits at d < 0.67 m needs ~4.3 s even accelerating at the minimum a_max = 0.8 m/s^2 (and is further capped at v_turn = 5 m/s on a turn connector). The conflict-clear gate covers this, which is fine, but the report must not present 4 s as a derived safety bound. Also 16 m/s is unreachable because v0_local = min(v0, v_limit) = 13.9 m/s (see contradictions).
- CLAIM: ML EVALUATION PROTOCOL: 'Report paired mean difference vs max_pressure +/- 1.96 SE over seeds' with 5 paired seeds, and 'a Wilcoxon signed-rank test is an optional scipy one-liner'.
  FIX: With n = 5 paired differences the 95% interval uses the t distribution with 4 df: +/- 2.776 SE, not 1.96. The Wilcoxon signed-rank test with n = 5 has a smallest attainable two-sided p of 0.0625 and can never reach 0.05, so it is useless at this sample size; either drop it or use >= 8-10 paired seeds (cheap: ~1 min each).
- CLAIM: RL RUNG: 'infeasible actions (switch during min green) masked in both action selection and the bootstrap target' with Stable-Baselines3 DQN; and 'replay 30k transitions (small: large buffers store stale multi-agent dynamics)' for the centralised Discrete(256) variant.
  FIX: SB3 DQN has no action masking (only MaskablePPO in sb3-contrib); masking the bootstrap target requires a custom policy. Use the already-offered alternative: only query the agent at applicable decision instants. The small-buffer rationale applies only to independent/parameter-shared learners; the centralised joint-action variant is a stationary single-agent MDP where buffer size is an ordinary hyperparameter (the disagreements section itself notes the earlier replay-buffer claim was backwards).
- CLAIM: VALIDATION EXPERIMENT (1): 'flow-density diagram must be triangular with jam density ~154 veh/km'.
  FIX: IDM does not produce a triangular fundamental diagram: the free branch is concave (flow falls off smoothly as v approaches v0 with the (v/v0)^4 term) and the congested branch is roughly linear. Expect 'approximately triangular' with the jam intercept at 1000/(l_veh + s0) = 154 veh/km and capacity 1700-1900 veh/h; do not fail the M0 gate on shape.
- CLAIM: ML RUNG 0 / DATASET: 'max_pressure: pressure_a = n_a - mean(down_n over a's three exits), skip blocked exits' and oracle_pressure_a '= n_a - (sum of down_n)/3, set to -1e9 if down_blocked for a's through exit'.
  FIX: Two different rules are given for blocked exits (exclude from the mean vs forbid the approach), and neither is max-pressure in Varaiya's sense (per-movement turn-ratio-weighted queue differences summed per phase, selecting the phase with maximal total pressure). The simplification is fine for a course, but pick one blocked-exit rule, implement it once (the label function IS the controller), and describe it in the report as 'a max-pressure-style heuristic', with the honesty caveat already in the text.
- CLAIM: DATASET VOLUME: 'signal_ticks ~120 x 4 x 650 = ~310k' rows and 'vehicles ~120 x 3000 = ~360k'.
  FIX: Episodes are 4200 s, not 3600 s, so ~750-800 decision rows per intersection (~370k total). Vehicles: 8 entries x <= 250 veh/h x 1.08 h of spawning <= 2200 per episode at the top of the band, ~1300 at design, so ~200k rows, not 360k. Harmless, but the student should size files from the measured 10-episode run.
- CLAIM: VEHICLE MODEL, free-flow time: 'free_flow_time_s = sum(edge_len / min(v0, v_limit)) + n_turns * (7 / v_turn)'.
  FIX: Through movements also traverse a 7 m connector (at ~v_limit, ~0.5 s each) that is in neither term, so every through crossing contributes ~0.5 s of phantom 'delay'. Add n_through * 7 / min(v0, v_limit).
